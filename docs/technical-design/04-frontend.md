Two structural decisions:

**Route groups by role, not by resource.** `(app)/employee/*`, `(app)/manager/*`,
`(app)/bookkeeper/*` each get a layout that asserts the role once. A URL is
therefore self-documenting about who may see it, and there is no page where "which
role am I rendering for?" is a question the component has to answer.

**`lib/queries/` separate from `lib/actions/`.** Reads and writes have different
shapes: queries are plain async functions called during render, actions are
`"use server"` entry points reachable from the browser. Keeping them apart makes
"is this reachable by an attacker?" answerable from the file path alone.

## 2. The authenticated shell

`app/(app)/layout.tsx` resolves identity once per request and hands it down, so no
child does its own auth round trip:

```tsx
export default async function AppLayout({ children }: { children: ReactNode }) {
  const ctx = await getContext();               // session + active membership
  if (!ctx) redirect("/login");
  if (!ctx.membership) redirect("/no-access");

  return (
    <AppShell role={ctx.membership.role} company={ctx.company} user={ctx.profile}>
      {children}
    </AppShell>
  );
}
```

Each role segment then adds its own guard:

```tsx
// app/(app)/manager/layout.tsx
export default async function ManagerLayout({ children }) {
  await requireRole(["manager", "bookkeeper"]);   // redirects, does not throw
  return <>{children}</>;
}
```

`middleware.ts` only refreshes the Supabase session cookie and bounces
unauthenticated users off `(app)` paths. It does **not** make authorization
decisions — middleware runs on the edge without database access, and a role check
there would either need to trust a JWT claim or be a second, drifting source of
truth. Authorization lives in RLS with layout guards as UX.

## 3. Component structure

Server Components by default. A component becomes `"use client"` only for
interactivity, and the boundary is pushed as deep as possible so payroll data is
not serialized into the RSC payload unnecessarily.

Example — the employee dashboard:

```
EmployeeDashboardPage                     (server) fetches v_salary_stats + v_leave_balance
├── StatCardGrid                          (server) plain rendering
│   ├── StatCard "Average net (12mo)"     (server)
│   ├── StatCard "Latest net" + TrendDelta(server)
│   └── VolatilityIndicator               (server) reads stddev/avg
├── NetPayTrendChart                      (client) Recharts needs the DOM
│   └── receives a pre-shaped {month, net, gross}[] — not raw rows
├── DeductionDonut                        (client) Recharts + hover tooltip
├── LeaveBalanceCards                     (server)
└── RecentPayslips                         (server)
    └── DownloadButton                    (client) useTransition + toast
```

The charts receive minimal arrays shaped by `lib/domain/insights.ts`, never whole
`payslips` rows. A `DownloadButton` is client-side only because it needs a pending
spinner; the authorization and URL minting happen in the action it calls.

Shared table behaviour lives in one `DataTable` built on TanStack Table headless
primitives, so the pay slip list, team list, and approvals queue get identical
sorting, empty states, and pagination without three implementations.

## 4. State management

There is no Redux, Zustand, or Context store for server data, because there is no
client-side cache to synchronize. State is classified and each class gets exactly
one home:

| State | Where it lives | Mechanism |
| --- | --- | --- |
| Server data (pay slips, requests, balances) | the server | RSC fetch + `revalidatePath` after mutations |
| Filters, sort, pagination, selected year | the **URL** | `searchParams` read by the Server Component |
| Form field values | the form | `react-hook-form`, uncontrolled inputs |
| Submission status + server errors | the action | `useActionState` |
| Optimistic pending rows | the component | `useOptimistic` |
| Ephemeral UI (dialog open, toast) | the component | `useState` |
| Session | cookies | Supabase SSR helpers |

Putting filters in the URL is the decision that pays off most. `?year=2025&status=pending`
means a manager can bookmark their pending queue, the back button behaves, a link
pasted to a colleague opens the same view, and filtering re-runs the query on the
server with a `WHERE` clause instead of shipping every row to the browser and
filtering in JS. Client state would have given us none of that and a bigger bundle.

Approving a request end-to-end:

```tsx
"use client";
export function ApprovalCard({ request }: { request: TeamRequest }) {
  const [state, submit, pending] = useActionState(approveTimeOffRequest, null);
  const [optimistic, setOptimistic] = useOptimistic(request.status);

  return (
    <form action={(fd) => { setOptimistic("approved"); submit(fd); }}>
      <input type="hidden" name="requestId" value={request.id} />
      <RequestStatusBadge status={optimistic} />
      <Button disabled={pending || optimistic !== "pending"}>Approve</Button>
      {state?.ok === false && <FormError>{state.error}</FormError>}
    </form>
  );
}
```

The badge flips instantly, the action revalidates
`/manager/approvals` on success, and a failure (say, another manager already
decided it) rolls the optimistic value back automatically and shows "This request
was already decided by someone else."

## 5. Validation

Three layers, each assuming the previous one may have been bypassed:

1. **Client** — `react-hook-form` + `zodResolver` on the same schema. Fast feedback,
   no round trip. Assumed defeatable.
2. **Server Action** — `schema.safeParse` inside the wrapper before any database
   call. This is the first layer that is actually trusted, because it runs where
   the user cannot reach it.
3. **Database** — `CHECK`, `UNIQUE`, `EXCLUDE`, `NOT NULL`, enums, foreign keys. The
   final guarantee, and the only one that holds under concurrency.

```ts
// lib/validations/time-off.ts
export const timeOffRequestSchema = z.object({
  leaveTypeId: z.string().uuid(),
  startDate: z.coerce.date().min(startOfToday(), { message: "Pick a future date." }),
  endDate: z.coerce.date(),
  reason: z.string().trim().max(500).optional(),
}).refine((v) => v.endDate >= v.startDate, {
  message: "End date must be on or after the start date.",
  path: ["endDate"],
}).refine((v) => differenceInCalendarDays(v.endDate, v.startDate) <= 90, {
  message: "Requests longer than 90 days need to be arranged directly.",
  path: ["endDate"],
});
```

Note what is **not** in the schema: `workingDays` and `employeeId`. Anything the
server can derive — from the company calendar or from the session — is never
accepted as input. A field that does not exist in the schema cannot be forged.

Money inputs are validated as strings and parsed to fixed-decimal values, never
via `parseFloat` into a `number` that gets rounded before it reaches
`numeric(12,2)`.

## 6. Error handling

| Failure | Handling | What the user sees |
| --- | --- | --- |
| Zod failure | `fieldErrors` returned from action | Inline message under the field |
| RLS denial (`42501`) | mapped to `FORBIDDEN` | "You do not have permission to do that." |
| Unique/exclusion conflict | mapped to `CONFLICT` | Specific, actionable sentence |
| Stale state (already decided) | RPC raises `P0001` | "Already decided by someone else." + list refreshes |
| Not found / no access | `notFound()` in the page | `not-found.tsx` |
| Query throws during render | nearest `error.tsx` | Segment-scoped error card with Retry; nav still works |
| Storage upload failure | action returns `INTERNAL`, no DB row written | "Upload failed, nothing was saved." |
| Unexpected | `INTERNAL` + trace id logged | "Something went wrong." + reference id |

Error boundaries are placed per route segment rather than only at the root, so a
failing chart on the employee dashboard does not blank the whole application.

Two rules for logging: server logs get full context (user id, company id, action
name, Postgres code), and responses to the browser get a generic message plus a
trace id. A raw Postgres error string in the UI leaks table and column names,
which is free reconnaissance for anyone probing the app.

## 7. Accessibility, i18n, and formatting

- The primary audience is Hebrew-speaking, so `dir="rtl"` with logical CSS
  properties (`ms-*`/`me-*`, never `ml-*`/`mr-*`) and a `dir="ltr"` island for
  numeric tables, where RTL mangles amount alignment.
- `Intl.NumberFormat("he-IL", { style: "currency", currency: "ILS" })` in one
  `<Money>` component, so no page invents its own formatting.
- Dates are stored as `date`/`timestamptz` and rendered in the company's timezone.
  A leave request for "March 1" must not become February 28 for a user whose
  browser is in UTC-5, which is why leave dates are plain `date` and never
  `timestamptz`.
- Charts carry a table equivalent behind a "View as table" toggle — the insights
  are the product's value, and they must be available to a screen reader.
